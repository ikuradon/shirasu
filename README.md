# shirasu

gpsd 経由で受信した「みちびき」の災害・危機管理通報をデコードし、Nostr に投稿する常駐プログラムです。受信には u-blox 形式を使います。

## 起動

Python 3.12.16 の Docker イメージを digest で固定して使用します。Linux ホストで gpsd が `127.0.0.1:2947` を待ち受け、受信機から災危通報を取得できることが前提です。本体の Compose サービスはホストのネットワークを使い、`host.docker.internal` を `127.0.0.1` に対応させます。

初回は設定例をコピーし、`config.py` を編集します。すでに `config.py` がある場合は上書きせず、既存設定を使ってください。

```sh
cp -n config.py.sample config.py
```

`SECRET_KEY` に Nostr の秘密鍵、`RELAY_URLS` に投稿先のリレー URL を指定します。複数のリレーはカンマで区切ります。gpsd の接続先は `GPSD_HOST` と `GPSD_PORT` で設定します。

```sh
docker compose up -d --build
```

`config.py` は Git 管理・イメージへのコピー対象から除外され、コンテナには読み取り専用で渡されます。

## 状態とログ

```sh
docker compose ps
docker compose exec shirasu python main.py --status --format text
docker compose exec shirasu python main.py --history
docker compose exec shirasu python main.py --history --state expired --limit 50
docker compose exec shirasu python main.py --show EVENT_ID
docker compose exec shirasu python main.py --status
docker compose logs --tail 100 -f shirasu
```

`--status` は保存済みの状態を JSON で表示します。送信待ち・送信済み・期限切れの件数、最後の受信・投稿時刻、接続状態、直近のエラーなどを確認できます。時刻は UNIX 秒です。状態確認では秘密鍵を読み込まず、DB を読み取り専用で開きます。

`--status --format text` は日本語で状態を表示し、最終受信などを「何秒前・何分前」で確認できます。接続状態は最後に保存された記録であり、状態更新が古ければそのことも表示します。
南海トラフのページ集約に対応した版では「南海トラフの集約待ち」も表示します。この変更は本番未反映です。

`--history` は保存中の配送履歴を新しい順に20件表示します。受信日時は JST、列は通報種別・配送状態・失敗回数・イベントID・最後の失敗理由です。`--state pending`（送信待ち）、`sent`（送信済み）、`expired`（期限切れ）で絞り込めます。`--limit` は1〜1000件、`--format json` で機械向けの出力も選べます。履歴の保持期間は配送時の重複情報と同じです。旧版から移行した行では、受信日時に移行元投稿の作成日時を使います。

各行は通報ごとの最新の配送状態です。「失敗回数」はアプリが記録した送信失敗の回数で、SDK 内部の再送回数は含みません。表では長い項目とイベントIDを短縮し、JSONでは完全な値を参照できます。確認コマンドは保存内容を読むだけで、再送・期限切れ処理・履歴削除を実行しません。`docker compose exec` の出力は実行した端末に表示され、常駐処理の `docker compose logs` には混ざりません。

`--show EVENT_ID` は保存済みの1通報を詳しく表示します。`EVENT_ID` を `--history` に表示される12桁のイベントID、または完全な64桁のIDに置き換えてください。16進数の大文字・小文字は区別しません。同じ先頭部分の記録が複数ある場合は選ばずにエラーを返すので、より長いIDを指定してください。検索対象は現在の投稿アカウントの保存記録です。

詳細には完全なイベントID、通報種別、配送状態、受信・送信日時（JST）、失敗回数、最後のエラー、保存当時の投稿本文と末尾のNMEAを表示します。本文は署名イベントに保存されたものを使い、現在の書式で整形し直しません。保存された本文を読み取れない場合も配送情報と読取エラーを表示します。本文中の端末制御文字はエスケープして、その旨を表示します。

`--show EVENT_ID --format json` は配送情報と本文をJSONで返します。JSONの `event.content` は保存当時の本文そのもので、文字のエスケープはJSONを解析すると元に戻ります。本文を読み取れない場合は `content` が `null`、`content_error` に理由が入ります。設定・秘密鍵・通信を使わず、保存状態の変更や再投稿も行いません。履歴の保持期限を過ぎて削除された記録は表示できません。

ヘルスチェックは、プロセスの動作、gpsd とリレーの接続、90秒以内の状態更新と通報受信を確認します。未解消の投稿エラーや90秒以上の送信待ちも異常と判定します。Docker の `unhealthy` 判定だけでは自動再起動しません。通常の通信切断はアプリ自身が再接続・再送し、プロセスが終了した場合は Compose の `restart: always` が再起動します。

起動・停止はログに記録します。公開 Nostr 投稿の `booting...` は送信しません。

本体と監視コンテナのログは Docker の `local` ドライバーで、各コンテナにつき10MB×3世代に制限します。ローテーション済みログは圧縮されます。通常どおり `docker compose logs` で参照でき、設定の反映にはコンテナの再作成が必要です。

監視用の `metrics` サービスは、状態DBを読み取り専用で参照し、`http://127.0.0.1:9016/metrics` に Prometheus メトリクスを公開します。本体とは別プロセスのため、本体の停止や状態更新の停滞も検出できます。収集設定・アラートルール・通知先の接続方法は [監視手順](monitoring/README.md) を参照してください。

未完了・保留事項は [TODO](TODO.md) に記録します。

画像URLを有効にすると、台風の連続通報を既定180秒でまとめ、署名付きの画像URLを投稿に添えます。
台風・震源に加え、v2で海上警報・震度・津波、v3で気象・緊急地震速報・火山を地図として外部のVercelサービスで描画します。v4では気象の情報ラベルを種別ごとに色分けします。現在の運用では、その他の通報は要旨画像です。

北西太平洋津波・降灰予報・指定河川洪水予報の専用画像は[オフラインプレビュー](image_service/README.md#未公開画像のプレビュー)で確認できます。本番投稿への反映は、他の画像の変更とまとめて行います。
他のQZQSM地図も、プレビューでは県境と拡大範囲を示す右下のミニマップに対応しています。
16種類・40ケースの公開版と作業版をまとめて比較する[オフライン画像ギャラリー](image_service/README.md#オフライン画像ギャラリー)も生成できます。投稿本文と添付画像をSNS幅で確認する「投稿全体」と「画像のみ」を切り替え、表示理由も確認できます。保存済みギャラリーを`--baseline`に指定すると前回の作業版と比較でき、変更したケースだけを絞り込めます。
画像の代替テキストは、情報種別・日時・訓練／取消／解除などを簡潔に説明し、ギャラリーで文面を確認できます。新規投稿の`imeta`へ同じ文面を付ける変更を実装済みです（本番未反映）。
[受信経過の投稿プレビュー](image_service/README.md#受信経過の投稿プレビュー)では、未完了通知から後着完成、収集中の訂正・取消、台風の追加受信を4つの合成訓練シナリオで確認できます。仮想時刻ごとに受信・収集状況・実際の投稿本文と作業版画像を表示します。
[描画時間と画像形式の計測](docs/image-benchmark.md)では、初回・再描画時間とPNG／WebP／JPEG／AVIFの容量・画素差を比較し、同じ画像をSNS幅と等倍で確認できます。
南海トラフは画像の有効／無効に関係なくページをまとめ、全文が揃えば1投稿にする変更を実装済みです。作業版では本文を重複させない見出しカードを添え、巨大地震注意・調査終了・取消の訓練例を確認できます。公開済みv1〜v4は見出しカードに未対応のため、対応版の一括公開までは新しい集約処理の画像添付を無効にしています。受信側の変更も本番未反映で、保存済みイベントと公開済み画像URLは維持します。
受信機には描画依存を追加せず、画像も永続保存しません。設定と運用は [画像の運用手順](IMAGES.md) を参照してください。

一括公開に向け、画像・受信側の候補パッケージを固定して署名URL、実PNG、投稿添付・ALT、旧URL、切り戻しを確認する
[通し検証の手順](docs/image-release-rehearsal.md)を用意しています。候補内だけでv5を登録し、通常配布と本番設定はv1〜v4のままです。
候補を使う受信側の起動は[公開用Compose設定](docs/release-compose.md)で準備します。検証したイメージへ固定し、既存DB・設定を引き継ぎます。本番への切替はまだ行っていません。
候補の正式なビルド・検証・保管は[GitHub Actionsの手順](docs/ci-release.md)へ集約します。手動workflowで検証済みイメージをprivate GHCRへ保存し、digestで復元して公開用設定へ接続します。

## 通報の再生・投稿プレビュー

保存した NMEA またはバイナリ UBX を読み、投稿文を端末へ表示できます。通報の整形と投稿対象の判定は本体と共通ですが、台風・南海トラフの集約配送は行いません。プレビューは設定・秘密鍵・配送DBを読み込まず、gpsdやリレーへの接続・署名・投稿も行いません。

ホスト上のファイルは、標準入力で渡すとコンテナへのコピーが不要です。

```sh
# 収録済みの2通報を使って表示を確認
docker compose exec -T shirasu python main.py --preview - \
  --received-at 2026-11-08T12:00:00+09:00 < tests/fixtures/preview.nmea

# 保存したUBXを解析
docker compose exec -T shirasu python main.py --preview - --input-format ubx \
  --received-at 2026-11-08T12:00:00+09:00 < recording.ubx
```

`--input-format` は `nmea`（既定値）か `ubx` です。UBXはu-bloxのRXM-SFRBXを含むバイナリ記録を指定します。通常のGPS文や他のメッセージが混在していても、対象の通報を抽出します。1つのファイルに含まれる複数通報を順番に表示し、`--preview /tmp/a.nmea /tmp/b.nmea` のように実行環境内の複数ファイルも指定できます。`-` は標準入力を意味し、1回だけ指定できます。

通報内の年月等は受信日時を使って補われるため、古い記録では `--received-at` にタイムゾーン付きの受信日時を指定してください。省略時はコマンド開始時の現在日時を使います。同じ入力を再現するときは同じ日時を指定します。ファイル内の各通報にも共通の基準日時を使い、元の受信間隔で待機する処理はありません。

投稿文は標準出力、読取エラーと件数の集計は標準エラーへ出します。各投稿文の前に出る区切りはプレビュー専用です。空・不明のDCX通報は本体と同様に除外し、重複した通報は入力された回数だけ表示します。過去の配送履歴による重複抑制は適用しません。
南海トラフも各ページを読み取った時点の表示になり、途中では「受信中」を示します。実投稿で使うSQLiteへのページ保存や、全ページが揃うまでの待ち合わせ・未完了通知は再現しません。

破損通報はエラーとして報告して後続の解析を続けます。エラーがある場合、または全入力から通報を1件も読み取れなかった場合は終了コード1です。正常に読めた通報がすべて投稿対象外だった場合は、表示0件・除外件数を報告して終了コード0になります。

## 投稿文の形式

海上警報は、見出し・JSTの発表時刻・警報ごとの対象地域に整理します。同じ警報をまとめ、警報の初出順と、その警報に属する地域の入力順を保ちます。地域の重複も省略せず、末尾に元のNMEAをそのまま付けます。

通常の海上警報は `【海上警報】発表（通常）`、訓練は `【訓練・試験】`、取消は `【取消】` を冒頭に表示します。訓練と取消が同時に指定されている場合は両方を表示します。訂正、優先区分、未定義コードの表示も保持します。「海上警報解除」は警報の種類として表示し、通報自体の取消とは区別します。

南海トラフは、見出し・情報種別・JSTの発表時刻・訓練／訂正／取消を本文で明示します。画像の有効／無効に関係なく受信ページをSQLiteに保存し、全ページが揃えばすぐに全文を1投稿として配送キューへ入れます。受信途中のページごとの投稿や、完成後の待ち時間はありません。見出しカード対応版では完成した本文と取消報に画像URL・`imeta`を添え、未完了通知は本文のみとします。公開済みv1〜v4では画像添付を無効にしています。この変更は実装済み、本番未反映で、画像変更の一括公開時に運用へ反映します。

最初のページから既定180秒で全文が揃わなければ、本文断片を含めず、見出し・情報種別・発表時刻・受信状況などのメタ情報を1回通知します。重複ページで締切は延ばしません。その後に不足ページを受信して全文が完成すれば、全文を追加で1回投稿します。受信途中のページと締切は再起動後も引き継ぎ、通常のDBバックアップにも含まれます。

訂正・取消では未確定の古い組立を抑制し、取消は待ち時間を置かずメタ情報を通知します。保存済みの署名イベントは変更しません。

海上警報・南海トラフ以外の単一通報は、従来どおり azarashi の本文を使います。画像機能を有効にした本体では台風を集約した本文と画像URLを付けます。単一通報のプレビューは集約待ちや画像署名を行わず、同梱サンプルの2件目で海上警報の書式を確認できます。

保存済みの署名イベントは作り直しません。更新前の送信待ちは元の文章・署名・イベントIDのまま再送し、投稿済みの通報も書式変更を理由に再投稿しません。

## 配送と重複防止

- 受信と送信を分離し、送信の再試行中も通報を受信します。空・不明の DCX 通報は投稿しません。
- 署名済みイベントを SQLite にコミットしてから送信します。再送・再起動後も同じイベント ID と署名を使います。
- 少なくとも1つのリレーから受理の ACK を得たら送信済みにします。全リレーへの配送を保証する方式ではありません。
- 送信は受信順の FIFO です。先頭が再送待ちの間は後続も待ち、警報と更新・解除の順序が逆転することを防ぎます。再試行の待ち時間は最大60秒です。
- 未送達のまま受信から15分が経過した通報は `expired` として記録し、新たな再送を開始しません。先頭の期限切れ後は次の通報へ進みます。
- 重複情報は最終受信または送達確認から24時間保持します。同じ通報を繰り返し受信している間は保持期間が延びます。
- 送信待ちの上限は1000件です。満杯で保存できなかった通報はエラーログと `dropped_full` カウンタに記録します。

ACK 受信と DB への成功記録の間に停止すると、次回は同じイベント ID を再送し、リレー側の重複抑制を利用します。システム全体での「exactly once」を保証するものではありません。

## 設定

既存の `config.py` に次の項目がなくても既定値で動きます。

| `config.py` の項目 | 既定値 | 内容 |
|---|---:|---|
| `RETRY_MAX_AGE_SECONDS` | `900` | 最初の受信から再送を続ける秒数。`0` は期限なし |
| `DEDUP_SECONDS` | `86400` | 同一通報の重複情報を保持する秒数 |
| `MAX_PENDING` | `1000` | 保存する送信待ち件数の上限 |
| `GPSD_READ_TIMEOUT` | `30` | gpsd からデータが届かないときに再接続するまでの秒数 |

送信中の履歴を早く消さないよう、`DEDUP_SECONDS` は `RETRY_MAX_AGE_SECONDS + 60` 以上にします。

`SHIRASU_STATE_PATH` 環境変数で DB の保存先を指定できます。Compose では `/data/shirasu.sqlite3`、直接実行時の既定値は `state/shirasu.sqlite3` です。`SHIRASU_LOG_LEVEL` の既定値は `INFO` です。

`SHIRASU_NANKAI_WAIT_SECONDS` は南海トラフのページが揃わないときに受信状況を通知するまでの秒数です。既定は180秒、範囲は1〜300秒で、`RETRY_MAX_AGE_SECONDS` が `0` 以外なら再送期限より短くします。画像設定とは独立して有効で、全文が先に揃えばすぐに投稿します。この設定はページ集約の変更とともに一括公開時に運用へ反映します。

`config.py` の変更は `docker compose restart shirasu` で反映します。Compose 側の環境変数・ボリューム設定を変えた場合は、`docker compose up -d` でコンテナを再作成してください。

## 永続データと停止

DB は Compose の名前付きボリューム `shirasu-state` に置きます。既定のプロジェクト名 `shirasu` では、Docker 上の名前は **`shirasu_shirasu-state`** です。署名済み公開イベント、配送履歴、状態と集約途中の通報を保存し、秘密鍵は保存しません。同じ DB を使う多重起動はロックで拒否します。

```sh
docker compose stop shirasu
```

停止時は SIGTERM を受けて受信と送信を終了します。Compose の終了猶予は20秒です。未送達イベントは DB に残り、次回起動時に期限内のものから再開します。

**本番の状態ボリュームを削除しないでください。** `docker compose down -v`、このボリュームへの `docker volume rm`、未使用ボリュームを削除する `docker volume prune -a` などで記録を消すと、未送達イベントと重複判定の記憶を失います。コンテナの再作成・イメージ更新ではボリュームを維持してください。DB は WAL を使うため、稼働中の `.sqlite3` ファイルだけをコピーしてバックアップしないでください。

旧版から空の DB へ切り替えると、それ以前の投稿は重複判定できません。初回移行では、過去24時間の自分の通報投稿を `Outbox.seed_sent()` で送信済み履歴へ登録してから切り替えます。以後は同じ状態ボリュームを継続して使用します。

## DBのバックアップと検証

Composeの `backup` サービスが1時間ごとに自動バックアップを作成し、ホストの `backups/auto/` に最新168世代を保持します。新規取得と検証に成功したときだけ古い自動分を整理し、手動のバックアップは対象にしません。`docker compose logs --tail 50 backup` で実行結果、`docker compose ps backup` でヘルス状態を確認できます。間隔・保持数の設定や停止方法は [バックアップ手順](BACKUP.md#composeの自動バックアップ) を参照してください。

バックアップの状態は既存の `metrics` サービスからPrometheusにも公開します。最終成功時刻、ワーカーの停止、作成・世代整理の失敗を監視し、設定した間隔の2周期以上成功していない場合などにアラートを評価します。詳細は [バックアップ監視](monitoring/README.md#自動バックアップの監視) を参照してください。

`--backup FILE` は稼働中の状態DBから整合したバックアップを作成し、DBの整合性・スキーマ・全アカウントの保存イベントの署名を検証します。出力は単体のSQLiteファイルで、既存ファイルは上書きしません。保存先の親ディレクトリは先に作成してください。

`--verify-backup FILE` はバックアップを読み取り専用で検証します。両コマンドとも既定は日本語の結果表示、`--format json` で機械向けの出力です。作成日時と状態記録の最終更新日時、全アカウントの送信待ち・送信済み・期限切れ件数を確認できます。設定・秘密鍵・通信は使用せず、原本の配送状態を変更しません。

ホストへの保存、別の保存先へのコピー、新しいボリュームへの復元は [バックアップと復元の手順](BACKUP.md) を参照してください。検証の成功は、バックアップ取得後の送信履歴まで揃っていることを保証しません。復元後の公開投稿再開には、その間の送信履歴の照合が必要です。

## テスト

ソースからテスト用イメージを作り、依存関係と回帰テストを確認します。`config.py`、受信機、Nostr リレーは不要です。テスト実行時はコンテナの外部通信を無効にします。

```sh
docker build --pull --tag shirasu:test .
docker run --rm --network none shirasu:test python -m pip check
docker run --rm --network none shirasu:test python -B -m unittest discover -s tests -v
docker build --target test --tag shirasu:integration .
docker run --rm --network none shirasu:integration python -B -m unittest discover -s tests/integration -v
```

回帰テストで、通報の除外・署名、通信切断後の復帰、保存・再送・順序・期限、再起動後の重複抑制を検証します。

[公開受信サンプル](tests/fixtures/qzqsm/README.md)もリポジトリに同梱しています。受信機の記録と公式L1Sアーカイブ由来の3ログ・333電文について、取得元のコミット・SHA-256・日付の復号基準を固定し、外部通信なしで再生します。南海トラフの全27ページの結合・重複・再起動・欠落後の追加受信、DCXの本文配送、各種地図の描画を検証します。公式訓練シナリオと照合した期待値と、合成した境界ケースを併用します。画像のテストは画像サービス用コンテナで実行します。

結合テストは、本物のアプリを別プロセスで起動し、ローカルの GPSD と Nostr リレーで TCP 切断・ACK 喪失・SIGKILL を再現します。再接続、再送時の署名とイベントID、配送順序、再起動後の重複抑制を検証します。テスト専用の WebSocket ライブラリは `test` ビルドターゲットだけに入り、本番イメージには入りません。

[GitHub Actions の Tests ワークフロー](.github/workflows/test.yml) は、`main` への push とプルリクエストで Compose 設定・Docker ビルド・依存関係・回帰テスト・結合テスト・アラートの発火と復旧を確認します。Actions 画面から手動実行もできます。CI では設定例を使い、秘密鍵や本番データを必要としません。

## 依存関係の更新

`requirements.in` は直接依存、`requirements.txt` は間接依存を含むバージョンと配布物の SHA256 を記録します。Docker ビルドはハッシュを照合し、固定していない依存や異なる配布物を拒否します。Linux AMD64・ARM64 の両方に対応します。

更新時は `requirements.in` を編集し、固定した Python 3.12 の一時環境で `pip-tools==7.6.2` を使って再生成します。

```sh
pip-compile --generate-hashes --no-emit-index-url --no-emit-trusted-host \
  --pip-args='--only-binary=:all:' --output-file=requirements.txt requirements.in
```

間接依存も更新する場合は `--upgrade` を付けます。Python 自体の更新時は Dockerfile のバージョンと multiarch digest を一緒に変更します。更新後は上記テストを実行し、両アーキテクチャ向けの wheel とハッシュを確認してください。テスト専用依存は `requirements-test.txt` に分離しています。
