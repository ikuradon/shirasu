# 未公開画像の地域投影・Path生成の再利用

固定範囲での不要な再計算を省いた`fbf446d`を基準に、地域の投影結果と
描画用Pathの頂点・コードを再利用します。対象は未公開の気象・緊急地震速報・震度・
海上・津波・降灰・DCX行政区域・取消背景です。
台風の受信位置や避難楕円など、通報ごとに変わる情報は保存しません。

## 実測結果

Linux aarch64・論理4CPU、Python 3.12.16、Matplotlib 3.11.2、NumPy 2.5.4、
Pillow 13.0.0で計測した再描画3回の中央値です。

| 入力 | 変更前 | 変更後 | 時間短縮 |
| --- | ---: | ---: | ---: |
| 緊急地震速報 | 6.272秒 | 3.176秒 | 49.4% |
| 震度情報 | 5.300秒 | 3.369秒 | 36.4% |
| 気象・複数区域 | 2.313秒 | 1.732秒 | 25.1% |
| DCX・複数県の区域 | 2.844秒 | 1.431秒 | 49.7% |
| 降灰・詳細 | 1.147秒 | 1.132秒 | 1.2% |
| 気象取消・明示元報参照 | 1.622秒 | 1.386秒 | 14.5% |

地域データが多い画像ほど効果があり、今回の降灰例はほぼ同じでした。
初回はキャッシュ作成の負荷があり、緊急地震速報15.017秒→16.316秒、震度14.094秒→14.863秒、
気象9.671秒→10.026秒、DCX11.685秒→12.066秒、降灰10.079秒→10.113秒でした。
気象取消は9.041秒→8.895秒です。初回の短縮を目的とした変更ではありません。

代表6例それぞれのプロセスのピークRSSは変更前349.7〜468.5 MiB、変更後347.8〜468.5 MiBで、
緊急地震速報は463.8→464.3 MiBでした。これは同じ画像を繰り返す独立プロセスの値です。
複数種類を続けて描くプロセスの値とは区別し、後述の描画バッファの保持も考慮します。

## キャッシュの単位と上限

`preview_geometry_cache.py`に、投影結果とPathデータを共通で管理するLRUを追加しました。

- 投影のキーは、元のgeometryの内容のSHA-256・レイヤー・正確な基準経度。
  区域コードだけでは識別せず、同じオブジェクトの座標を変更した場合も再計算します。
  基準経度の丸めや360度単位への統合は行いません。
- Pathのキーは、ポリゴン・穴の構造と順序、および投影済み座標のバイト列。
  頂点が同じでも「外周と穴」と「独立した2区域」を混同しません。
- 未登録時は公開済みの幾何処理を呼び出します。検証・投影・巻き方向の計算を独自に
  書き換えず、例外も保存しません。投影だけを使う処理ではPathを生成しません。
- 配列は変更不能なbytesを裏付けにします。Pathの軽いラッパーと描画オブジェクトは
  毎回作るため、色・線幅・クリップ・Pathの属性が次の投稿へ混ざりません。
- **最大256項目・保持量の概算32 MiB**を共通上限とし、超える場合は古い項目から退避。
  1項目で容量を超えるものは保存せず、通常どおり描画します。
  サイズには座標データだけでなくキー・tuple・NumPy配列などの管理領域も含めます。

容量はプロセス全体のRSS上限ではありません。元の地理アセット、描画中の画像、
一時的な計算領域や退避後も描画中の図が参照しているデータは別です。
再起動するとキャッシュは空になります。ディスク保存や外部サービスは使用しません。

JSONの直列化ではtupleとlistなどが同じ表現になるため、厳密なJSON型でない入力は
キャッシュを経由せず従来の検証へ渡します。これにより、変更前なら拒否された形へ
データを書き換えても、既存のキャッシュで検証をすり抜けません。

## 検証方法

変更前の6モジュールを`fbf446d`から抽出し、それ以外のコード・アセット・依存が同じ
Docker環境で比較します。固定範囲の高速化は変更前後の双方に含まれています。
入力ごと・変更前後ごとに新しいプロセスと空のフォントキャッシュを用意し、初回1回と
再描画3回を直列に測ります。変更前は固定したコミットの計測値を使用し、変更後は
最終コードで再計測します。入力・環境・固定範囲のコードが一致することも確認します。

計測時間はPNG生成までを含み、import・メモリ量の取得・画像照合は含みません。
OSのファイルキャッシュは消去しません。主図・ミニマップの範囲は別の描画で記録します。
代表6例の比較に加え、49入力を通常順・逆順の2周、同じプロセスで描画し、全PNG・
表示判定・キャッシュ上限・退避を確認します。2周の描画時間は初回性能の比較には使いません。
メモリ量はキャッシュの保持量と、プロセスの現在RSS・ピークRSSを分けて記録します。

最終の計測・照合記録は`dist/geometry-reuse-final/`へ保存し、従来の`dist/preview/`、
`dist/benchmark/`、`dist/map-bounds/`は比較基準として保持します。

回帰テスト121件はすべて成功しました。入力変更・穴や日付変更線・LRU・容量超過・
変更不能な配列・色の独立性に加え、DCXで複数の不備が重なる場合の検証順も確認しています。
公開版用45ファイル（コード・アセット・依存設定）は`fbf446d`とバイト単位で一致し、
新しいキャッシュはプレビュー専用の配布リストだけに追加しています。
公開版PNG・既存の署名URL・配布物の分離も回帰テストで確認済みです。

記録は`comparison.json`、`all-images/result.json`、`gallery-comparison.json`、
`tests.json`、`frozen-sources.json`です。
変更前後のソースと計測スクリプト、メモリ診断の記録も同じディレクトリに保存します。

全49入力の2周・98回すべてで、承認済みプレビューと一致済みの基準PNGにバイト単位で一致し、
順序を変えても表示判定は変わりませんでした。代表6例は変更前後で主図・ミニマップの範囲・
表示位置・表示判定も一致しています。キャッシュは最大89項目・概算31.962 MiBで、
70項目の退避が発生した後の再描画も一致しました。
承認済みギャラリーの40ケース・46投稿についても、2周分の172使用箇所でPNGと表示判定を
直接照合し、すべて一致しています。

この98回を続けたプロセスのピークRSSは1,146.95 MiBです。32 MiB以下に保たれていた
キャッシュだけの値ではなく、複数種類のアセットと下記の描画バッファ保持も含みます。

## 連続描画時の既存メモリ保持

キャッシュの保持量とは別に、FigureとCanvasの循環参照によって、完成した図の
AggバッファがGCまで残る挙動を確認しました。同じ気象画像を20回描いた後のRSSは、
変更前556.97 MiB、変更後549.77 MiBで、両方ともFigure・Canvas・RendererAggが各20個
残っていました。完全GC後は弱参照で確認した残存数がすべて0になり、60回の比較描画で
PNGは一致しています。確保済み領域がallocatorに残るため、RSSは直ちには戻りません。

描画ごとの完全GCを診断用に試すとRSSは293.56 MiBで安定しましたが、中央値219.8ミリ秒の
追加処理が必要でした。今回はキャッシュに起因する増加ではないことを切り分けるまでとし、
図の解放方法・GCの頻度を調整する改善は別TODOに記録します。毎回のGCは導入していません。
この結果からも、キャッシュの32 MiB上限をプロセス全体のメモリ上限とは扱いません。

## 再測定

画像用の依存とアセットを準備した環境で、既存の計測機能を使用できます。

```sh
python -B scripts/benchmark_images.py --output dist/benchmark-geometry-reuse \
  --case eew --case seismic-intensity --case weather-many \
  --case dcx-prefectures --case ash-detail --case weather-cancel-reference \
  --warm-repeats 3 --encoding-repeats 1
```

既存出力は上書きしません。形式変換は描画時間の計測後に行います。
ここでの結果はローカル環境での値で、Vercelの実応答時間ではありません。
